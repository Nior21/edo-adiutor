# Анализ свойств ЭТрН для табличной части 1С

Ниже — разбор всех свойств документа `ЭлектроннаяТранспортнаяНакладная` из вашего XML. Логика такая: **что можно смело убрать** из табличного отображения, потому что оно либо всегда пустое, либо дублирует другие поля, либо не несёт диагностической ценности при разборе проблем с ЭТрН.

---

## 1. Служебные/системные поля 1С — оставить обязательно

| Свойство | Почему оставить |
|---|---|
| `Ref` | Идентификатор документа, нужен для перехода/поиска |
| `DeletionMark` | Признак удаления — важно для фильтрации «мусора» |
| `Date`, `Number` | Базовые реквизиты документа |
| `Posted` | Проведён/не проведён |
| `Организация` | Ключевой реквизит |
| `ВидДокумента` | Тип ЭДО |
| `ЭтоВходящий` | Входящий/исходящий — критично для анализа |
| `РольУчастника` | Кто мы в документе (1/2/3) — критично |

### 2.2. Дублирующие «Дата/Время формирования файла»

Для каждого титула есть **три** поля:
- `...ДатаФормированияФайла` (дата)
- `...ВремяФормированияФайла` (время, но с «мусорной» датой `0001-01-01`)
- `...ИдентификаторФайла`

Для анализа проблем достаточно **одного** поля — `ИдентификаторФайла` (есть/нет) + `ДатаФормированияФайла`. Поле `ВремяФормированияФайла` хранит время в странном формате (`0001-01-01T13:15:07`), и его ценность сомнительна.

**Можно убрать:**
- `ТитулГрузоотправителяВремяФормированияФайла`
- `ТитулПеревозчикаПриемкаВремяФормированияФайла`
- `ТитулГрузополучателяВремяФормированияФайла`
- `ТитулПеревозчикаВыдачаВремяФормированияФайла`

(и все `ДопТитул...Время...`, которые уже перечислены выше)

---

### 2.3. Поля-идентификаторы, дублирующие ссылки на контрагентов

В документе есть два набора:
1. `СсылкаТитулГрузоотправителяГрузоотправитель`, `...Грузополучатель`, `...Перевозчик` — ссылки на справочники 1С.
2. `ИдентификаторГрузоотправителя`, `ИдентификаторГрузополучателя`, `ИдентификаторПеревозчика` — строковые ID из ЭДО.

Для **анализа проблем с ЭТрН** полезны оба набора, но:
- Если задача — «почему не уходит/не принимается», важнее **Идентификаторы** (они уходят в роуминг).
- Если задача — «кто это у нас в базе», важнее **Ссылки**.

**Рекомендация:** не убирать полностью, но в табличной части показывать только `Идентификатор...` (они компактнее и чаще «ломаются»), а `Ссылка...` оставить в карточке.

### 2.4. Поля, которые есть, но не несут ценности для анализа

| Свойство | Почему можно убрать |
|---|---|
| `ТитулГрузоотправителяИдентификаторФайла` | Дублируется с `УИДМинтранс` + датой; для диагностики достаточно факта «есть/нет» |
| `ТитулПеревозчикаПриемкаИдентификаторФайла` | То же |
| `ТитулГрузополучателяИдентификаторФайла` | То же |
| `ТитулПеревозчикаВыдачаИдентификаторФайла` | То же |
| `ТекущийПолученныйТитул` | Служебное поле состояния; полезно только в момент разбора, не в таблице |
| `ТекущийТитул` | То же |
| `ТекущийШаг`, `ТекущийШагВыполнен` | Служебные поля бизнес-процесса; в таблице дублируют `ТекущийТитул` |
| `ИныеПолучателиСтрока` | Во всех документах пусто |
| `Комментарий` | Во всех документах пусто |
| `ЭтоКонтейнернаяПеревозка` | Во всех `false`, но может пригодиться — оставить как флаг |
| `УИДМинтранс` | **Важно оставить** — это ключ для поиска в ГИС ЭПД |

## 4. Отдельно: что реально «ломает» ЭТрН

Судя по данным, проблемы могут быть в:
- пустых `ИдентификаторГрузополучателя` / `ИдентификаторПеревозчика` (док. 00000000001, 00000000002);
- `DeletionMark = true` при наличии титулов (док. 777, 881/2, 881/4);
- расхождении `ТитулГрузоотправителяТранспортнаяНакладнаяНомер` и `Number` (док. 882: Number=882, а ТНН=881/3);
- `ЭтоВходящий = true` при `РольУчастника = 2` (док. 779 — мы грузополучатель, это входящая).

Именно эти поля и стоит выводить в первую очередь.
