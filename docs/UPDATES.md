# Обновление внешней обработки (.epf)

## Модель (v0.6.1+)

1. Пользователь открывает обработку **из файла** (чаще всего `bin\ПомощникДляЭДО.epf`).
2. Один раз указывается **якорный** `.epf` («Выбрать файл…») — путь сохраняется в хранилище общих настроек.
3. Рядом с якорем хранится архив **`releases\{version}\ПомощникДляЭДО.epf`** (+ `manifest.json`). Для пользователя путь «Файл → Открыть» **всегда один** — якорный `bin\ПомощникДляЭДО.epf`; при обновлении его **подменяют** копией из нужного релиза (текущий сеанс остаётся в памяти).
4. Манифест обновлений:
   - **Прод:** `ObjectModule.URLМанифестаОбновлений()` → HTTPS JSON (например `raw.githubusercontent.com/.../bin/update-manifest.json`).
   - **Разработка:** пустой URL → читается `bin/update-manifest.json` рядом с якорным `.epf`.
5. Если на диске или в манифесте есть версия **новее текущей**:
   - при необходимости файл **скачивается** в `releases\{version}` (повторно не качается, если уже есть);
   - якорный `.epf` в корне `bin` перезаписывается из `releases\{version}`;
   - подключение новой копии через платформенный API (`Выполнить(...)`: в EPF прямой вызов недоступен при компиляции); при необходимости `.epf` передаётся на сервер во временный файл, затем **новое окно** формы;
   - в старом окне React блокируется overlay «это окно устарело — закройте».
6. Клик по **vX.Y.Z** в статус-баре — список локальных релизов на ПК, открытие выбранной версии в новом окне. Старые `.epf` **не удаляются**.

Автопереключение после проверки (с баннером/overlay, не «тихое»): если задан якорь и есть более новая целевая версия, через ~0,2 с запускается тот же сценарий «скачать при необходимости → новое окно».

## Подмена якоря и запущенный сеанс

Скомпилированная обработка уже **в памяти** — подмена файла на диске **не прерывает** текущее окно. Новые запуски и «Файл → Открыть» всегда идут в один путь (`bin\…epf`). Копии версий остаются в `releases` для отката. Если файл занят другим процессом, подмена может не пройти — тогда откроется новое окно из уже скачанного релиза, а якорь обновят при следующей попытке.

## Формат манифеста

`bin/update-manifest.example.json`:

| Поле | Описание |
|------|----------|
| `version` | Semver `x.y.z` |
| `epfUrl` | Прямая HTTPS-ссылка на `.epf` (GitHub Releases asset или raw) |
| `notes` | Текст для пользователя |

## Сборка и релиз

```powershell
# React → Template.bin
.\scripts\pack.ps1

# EPF из EDT в bin\ПомощникДляЭДО.epf, затем:
.\scripts\prepare-release.ps1 -RepoBaseUrl "https://raw.githubusercontent.com/ORG/REPO/main/bin"
```

Скрипт копирует EPF в `bin\releases\{version}\`, пишет `bin/update-manifest.json`.

### CI (GitHub Actions, эскиз)

- `pack.ps1` + выгрузка EPF (DESIGNER/EDT headless, если настроено).
- `prepare-release.ps1` с `-RepoBaseUrl`.
- Публикация артефактов: `update-manifest.json`, `releases/**`.
- В `ObjectModule` для релизной ветки — URL raw-манифеста.

Регистрация в справочнике доп. обработок — **отдельный этап**; `СведенияОВнешнейОбработке()` уже заготовлено.

## Закрытый код, обфускация и публичный GitHub

| Подход | Суть |
|--------|------|
| **Закрытый модуль** в конфигурации/обработке | В EDT: свойства модуля → «Закрытый» + пароль. В **выгруженном .epf** модуль остаётся в бинарном виде; исходники в git — отдельный вопрос лицензии. |
| **Публичный репозиторий** | Обычно выкладывают **исходники EDT + React**, а **готовый .epf** — через Releases/manifest. Так делают многие open-source EPF; «бана» за это нет, если не нарушать лицензию 1С и не публиковать чужие типовые конфигурации. |
| **Обфускатор BSL** | Редко нужен, если исходники не в git; для .epf достаточно закрытого модуля. Обфускация усложняет поддержку и отладку. |

Рекомендация: **исходники в приватном или public repo**, **дистрибутив — только .epf** (и manifest); при необходимости — пароль на модули перед выгрузкой EPF.

## Ограничения

- Скачивание `epfUrl` — **HTTP(S)** на сервере 1С; `file://` не поддерживается.
- Нужны права записи в каталог якорного `.epf`.
- Если обработка открыта не из файла — укажите якорь вручную.
